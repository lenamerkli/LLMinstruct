You *can’t* install `lingua-language-detector==2.1.1` because, although the release exists on PyPI, **PyPI does not provide any distribution file (wheel/sdist) that matches your current Python interpreter**.

### What’s happening (why PyPI shows it but pip won’t install it)
`pip` doesn’t install “a version” in the abstract. It installs a **distribution file** for that version (usually a `.whl` wheel, sometimes a source tarball). Wheels are built for specific combinations of:

- Python version / implementation (e.g. CPython 3.13 is `cp313`)
- ABI
- OS / architecture (Linux x86_64, Windows amd64, macOS arm64, …)

This compatibility is encoded in **wheel tags**.

For `lingua-language-detector==2.1.1`:

- It **requires Python >= 3.10**.
- **There is no source distribution** (“No source distribution files available for this release”).
- The published wheels are only for **CPython 3.10–3.13** (and some PyPy builds), not for newer CPython versions.

So if you’re on **Python 3.14+**, `pip` can’t find a compatible wheel for 2.1.1, and since there’s **no sdist**, it has nothing to build from—resulting in:

> `No matching distribution found`

### Your error strongly suggests you’re on Python 3.14 (or newer)
This part is the giveaway:

- `1.3.5 Requires-Python ... <3.13` was ignored
- `1.4.0/1.4.1/1.4.2 Requires-Python ... <3.14` was ignored

That pattern matches **Python >= 3.14** (because `<3.14` excludes 3.14+). Meanwhile, `pip` falls back to older versions like `1.3.4` that don’t exclude your Python version in the same way.

### How to fix it (pick one)

#### Option A (most common): use Python 3.13 (or 3.12) for this project
Install/activate Python 3.13, create a venv, then install:

```bash
python3.13 -m venv .venv
source .venv/bin/activate   # (Windows: .venv\Scripts\activate)
python -m pip install -U pip
python -m pip install lingua-language-detector==2.1.1
```

This works because 2.1.1 provides wheels up through CPython 3.13.

#### Option B: stay on Python 3.14+, but use the pure-Python 1.x line
The project explicitly maintains **both**:
- `2.x` = Rust-native extension bindings (fast, but needs matching wheels)
- `1.x` = pure Python implementation (more portable)

On Python 3.14+, you may be forced onto an older 1.x that doesn’t declare `<3.14` (your log shows `1.3.4` is installable).

```bash
python -m pip install "lingua-language-detector==1.3.4"
```

#### Option C: build from source (advanced, not “pip install from PyPI”)
Because PyPI has **no sdist** for 2.1.1, pip can’t compile it automatically.
If you’re comfortable with Rust tooling, you can try building from the GitHub source tag `v2.1.1` (this may or may not work on Python 3.14 depending on upstream support).

### Quick sanity checks you can run locally
These will confirm the root cause in seconds:

```bash
python -V
python -m pip --version
python -m pip debug --verbose
```

If `python -V` prints `3.14.x`, that’s exactly why `2.1.1` won’t match any available wheel for your interpreter.

### Extra context: why 2.x is “pickier”
Starting from **2.0.0**, the package moved from pure Python to **compiled Rust bindings** for performance.
That’s great for speed, but it means you’re dependent on the maintainer publishing wheels for each new CPython (3.10, 3.11, 3.12, 3.13, …). When you jump to a brand-new Python (like 3.14), you often have to wait for wheel support.
