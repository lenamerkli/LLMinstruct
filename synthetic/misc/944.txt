How can I fix the full /var/log ?
§a§
`/var/log` is not on your main disk. It is mounted on **`/dev/zram1`**, a tiny **47 MB RAM-backed filesystem**, and that is what is full.

So the problem is **not** that `/` is full.
Your root filesystem still has about **9.1 GB free**.
The issue is that `/var/log` was intentionally put on a very small zram device.

Also, the `/dev/loop* 100%` lines are normal for Snap packages.

## What to do

### 1) See what inside `/var/log` is using space
Run:

```bash
sudo du -xhd1 /var/log | sort -h
sudo find /var/log -xdev -type f -printf '%10s %p\n' | sort -n | tail -20
sudo journalctl --disk-usage
```

That will show whether the space is mostly:
- `systemd-journal`
- `syslog`
- `kern.log`
- `auth.log`
- some app writing too much

---

### 2) Quick safe cleanup
If systemd journal is large:

```bash
sudo journalctl --rotate
sudo journalctl --vacuum-size=10M
```

Force logrotate:

```bash
sudo logrotate -f /etc/logrotate.conf
```

Check again:

```bash
df -h /var/log
```

---

### 3) Emergency cleanup if still full
If one or two active logs are huge, truncate them:

```bash
sudo truncate -s 0 /var/log/syslog
sudo truncate -s 0 /var/log/kern.log
sudo truncate -s 0 /var/log/auth.log
```

If there are old rotated logs:

```bash
sudo find /var/log -type f \( -name "*.gz" -o -name "*.1" \) -ls
```

You can remove old rotated logs if you do not need them:

```bash
sudo find /var/log -type f -name "*.gz" -delete
```

Be careful not to blindly delete everything in `/var/log`.

---

## Permanent fix

Because `/var/log` is only **47 MB**, it will likely fill again. You have 3 real options:

### Option A: Increase the zram size for `/var/log`
This is best if the system was set up this way to reduce SD/eMMC wear.

First identify what created the zram mount:

```bash
mount | grep ' /var/log '
systemctl list-units --type=service | grep -Ei 'log2ram|zram'
dpkg -l | grep -Ei 'log2ram|zram|armbian'
```

Common possibilities:

- `log2ram`
- `armbian-zram-config`
- `systemd-zram-generator`

If it is `log2ram`, the config is commonly:

```bash
sudo nano /etc/log2ram.conf
```

Look for something like:

```bash
SIZE=40M
```

Increase it, for example:

```bash
SIZE=128M
```

Then restart or reboot:

```bash
sudo systemctl restart log2ram
```

or

```bash
sudo reboot
```

---

### Option B: Disable zram for `/var/log`
If you do not need logs in RAM, disable the feature so logs go to disk normally.

Again, identify the service/package first. For example, if it is `log2ram`:

```bash
sudo systemctl disable --now log2ram
sudo apt remove log2ram
sudo reboot
```

If it is Armbian or another zram service, the package/service name will differ.

This is the simplest long-term fix if disk wear is not a concern.

---

### Option C: Keep zram but reduce log growth
If a service is spamming logs, fix that too, or the zram will refill quickly.

Useful commands:

```bash
sudo systemctl --failed
sudo journalctl -p err -b
sudo journalctl -b | tail -100
```

If `rsyslog` or some app is flooding logs, identify and fix that service.

---

## Good default fix
If you want the practical approach:

1. Free space now:
   ```bash
   sudo journalctl --rotate
   sudo journalctl --vacuum-size=10M
   sudo logrotate -f /etc/logrotate.conf
   ```

2. If still full, truncate big active logs:
   ```bash
   sudo truncate -s 0 /var/log/syslog /var/log/kern.log /var/log/auth.log
   ```

3. Then either:
   - increase zram size, or
   - disable `/var/log` on zram entirely

---

Because `/var/log` is mounted separately on zram, **deleting files from `/` will not fix `/var/log`**.

§a§
The reason the size didn't change is that `armbian-ramlog` cannot resize a partition that is currently mounted and **100% full**. When you run `restart`, the script tries to sync the logs to the SD card and unmount the drive. Because it is completely full, the sync/unmount process likely failed silently, leaving the old 50MB device in place.

Follow these steps to force the change:

### Step 1: Clear the "Full" status immediately
You must free up some "breathing room" so the scripts can execute. Truncate the largest files:

```bash
# This empties the files without deleting them (safer for active processes)
sudo find /var/log -type f -exec truncate -s 0 {} +
```

### Step 2: Force the service to stop and unmount
A `restart` command often fails if the mount is "busy." We will stop it manually:

```bash
sudo systemctl stop armbian-ramlog
sudo systemctl stop armbian-zram-config
```

Check if it's still mounted: `df -h | grep /var/log`. If it is still there, force unmount it:
```bash
sudo umount -l /var/log
```

### Step 3: Clear the ZRAM device
Now we remove the actual ZRAM block device so it can be recreated with the new size:
```bash
# Look for which zram is /var/log (usually zram1 based on your output)
# This resets the device
echo 1 | sudo tee /sys/block/zram1/reset
```

### Step 4: Start the services back up
Now that the old device is destroyed, starting the service will read your new `250M` config:

```bash
sudo systemctl start armbian-zram-config
sudo systemctl start armbian-ramlog
```

### Step 5: Verify
Run `df -h` again. You should now see:
`/dev/zram1       250M    ...  /var/log`

---

### If the above doesn't work (The "Reboot" method)
Armbian’s ZRAM services are heavily integrated into the boot sequence. If the manual steps above don't work because the filesystem is locked by Docker or other processes:

1. Ensure `/etc/default/armbian-ramlog` has `SIZE=250M`.
2. Ensure `/etc/default/armbian-zram-config` is saved.
3. **Reboot the server.**

### Important: Why it filled up so fast
Even with 250MB, if you have a runaway log, it will fill up again. I strongly recommend checking your Docker logs. Run this to see what is currently spamming your logs:

```bash
# See the last 100 lines of the system log to find the culprit
tail -n 100 /var/log/syslog
```

If you see a lot of Docker-related lines, follow the **Option 4 (Docker daemon.json)** step from my previous message to limit Docker's log sizes, otherwise, they will eventually overwhelm even the 250MB partition.
