§a§
Your schema looks very solid and well-structured. It covers the core requirements of a personal cloud application: storage hierarchy (drives -> partitions -> entries), permissions (shares), and metadata (tags, types).

Here is a breakdown of what works well, along with a few critical points and suggestions to make the database production-ready.

### **Positive Aspects**

1.  **Ownership Model:** You have clearly separated ownership (`owner_id`) from access (shares). This is crucial for multi-user capabilities.
2.  **Soft Deletes:** Using `deleted TEXT NULL` and `hidden INTEGER` instead of hard deletes is an excellent design choice. It allows you to recover files or maintain folders that have been emptied.
3.  **Linking Strategy:** By using `target_id` and `target_partition_id` for links, you are creating "shallow links" (shortcuts) rather than duplicating data. This is very storage-efficient.
4.  **Granular Permissions:** The `allow_write` column in shares (0 vs 1) gives you a simple way to handle read-only vs. read-write permissions.

### **Critical Missing Piece: The `users` Table**

Your schema relies heavily on `users(id)` but never defines the `users` table. You need a place to store usernames, email, passwords (hashed), and profile info.

**Add this immediately:**

```sql
CREATE TABLE IF NOT EXISTS users (
    id TEXT PRIMARY KEY,
    username TEXT NOT NULL UNIQUE,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL, -- never store plain text!
    role TEXT DEFAULT 'user',   -- e.g., 'user' or 'admin'
    created TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### **Specific Improvements & Suggestions**

#### 1. Partition Capacity
Currently, `partitions` has a `capacity INTEGER`, but there is no mechanism to track **usage**.
*   **The Problem:** Your app knows the capacity (e.g., 100GB), but it doesn't know how much of that 100GB is currently being used by the `entries` in that partition.
*   **The Fix:** Depending on your app's complexity, you might want to either:
    *   **Calculate on the fly:** Do a recursive query for folder sizes (computationally expensive on large databases).
    *   **Add a summary table:** Create a table that tracks total size per partition.
    *   **Use a default capacity:** If it's just a quota limit (like Dropbox), you keep it as a static number, but you might want to add a `last_quota_sync` timestamp to know if the limit is outdated.

#### 2. Storage Backend (Where is the file?)
The `entries` table stores metadata (`size`, `hash`, `name`), but it **does not** store the actual file content.
*   **Clarification:** Are your files stored in a Blob field in the DB (SQLite has a specific "Blob" type, but it's inefficient for large files), in S3 buckets, or on a local filesystem?
*   **Recommendation:** Since you are making a cloud app, you likely need a `storage_service` table to abstract where the data lives (e.g., "Amazon S3 Bucket X").

#### 3. The `target_partition_id` Redundancy
In your `entries` table:
```sql
target_id TEXT NULL,
target_partition_id TEXT NULL
```
If `type='link'`, you are pointing to another entry via `target_id`.
*   **Suggestion:** `target_partition_id` is likely redundant here. If `target_id` exists, you can derive the partition from that entry. Keep it if you plan to have links that point to "Root" of a partition rather than a specific folder, but if you always link to entries, remove it to clean up the schema.

#### 4. Indexes for Performance
Since you have a tree structure (`parent_id`) and a sharing structure (`entry_id`, `user_id`), you should add indexes to ensure fast lookups.
*   **For Navigation:** Ensure you have an index on `parent_id` inside the `entries` table so opening a folder is instant.
*   **For Search:** An index on `tags` and `tag_relations` is good.

```sql
-- Add these to your schema after creating the table
CREATE INDEX IF NOT EXISTS idx_entries_parent ON entries(parent_id);
CREATE INDEX IF NOT EXISTS idx_tag_relations_entry ON tag_relations(entry_id);
```

#### 5. Duplicate Shares
In `entry_shares` and `partition_shares`, you allow a user to share an item with themselves multiple times (e.g., Create Share 1, Create Share 2, Create Share 3). This can be confusing.
*   **Fix:** Add a `UNIQUE` constraint to the table if you don't need multiple share records for the same permissions.

```sql
-- In entry_shares
FOREIGN KEY (entry_id) REFERENCES entries(id),
FOREIGN KEY (owner_id) REFERENCES users(id),
FOREIGN KEY (user_id) REFERENCES users(id),
UNIQUE(entry_id, user_id, allow_write) -- Prevents duplicates
```

### **Summary**
The logic is sound. Once you add the `users` table and clarify where the file content is physically stored, you have a solid foundation for a personal cloud storage app
