What are some good QEMU managers for fedora linux?
§a§
Fedora Linux is one of the best distributions for virtualization because it ships the latest versions of the QEMU/KVM stack. Depending on whether you want "it just works" simplicity or deep technical control, here are the best QEMU managers for Fedora:

### 1. Virt-Manager (Virtual Machine Manager)
**Best for:** Power users and desktop virtualization.
Virt-Manager is the "gold standard" for managing QEMU/KVM on Linux desktops. It provides a comprehensive interface that allows you to tweak almost every aspect of the VM's hardware, from CPU pinning and XML editing to USB passthrough.

*   **Key Features:** Direct XML editing, snapshots, remote management via SSH, and support for complex networking.
*   **Installation:** It is often included in Fedora's virtualization group.
    ```bash
    sudo dnf install @virtualization
    # Then start the service
    sudo systemctl enable --now libvirtd
    ```

### 2. GNOME Boxes
**Best for:** Beginners or quickly testing ISOs.
Pre-installed on Fedora Workstation, GNOME Boxes is a highly simplified front-end for QEMU. It automates most of the configuration (RAM, disk, and drivers) so you can get a VM running in just a few clicks.

*   **Key Features:** "Express Install" for many distros, automatic driver configuration (via spice-vdagent), and a clean, modern interface.
*   **Installation:**
    ```bash
    sudo dnf install gnome-boxes
    ```

### 3. Quickemu & Quickgui
**Best for:** Quickly spinning up optimized Windows, macOS, and Linux VMs.
Quickemu is a command-line tool designed to create highly optimized virtual machines automatically. It handles the "best" QEMU settings for performance out of the box. **Quickgui** is its community-made graphical interface.

*   **Key Features:** One-click downloads of OS images (including Windows and macOS), pre-configured hardware optimization, and seamless folder sharing.
*   **Installation:** Quickemu is natively available in the Fedora 41+ repositories.
    ```bash
    sudo dnf install quickemu
    ```
    *Note: Quickgui is usually installed via AppImage or from its GitHub releases page.*

### 4. Cockpit (with `cockpit-machines`)
**Best for:** Servers or headless Fedora setups.
If you are running Fedora Server or want to manage your VMs through a web browser, Cockpit is the ideal choice. It uses the `libvirt` backend but presents everything in a clean web dashboard.

*   **Key Features:** Web-based console access, resource monitoring (CPU/RAM graphs), and easy management of multiple host machines from one tab.
*   **Installation:**
    ```bash
    sudo dnf install cockpit cockpit-machines
    sudo systemctl enable --now cockpit.socket
    ```
    *Access it at `https://localhost:9090`.*

### 5. Incus
**Best for:** A "private cloud" experience on your laptop.
Incus (the community fork of LXD) is a powerful daemon that manages both system containers and full QEMU virtual machines. It feels more like using a public cloud (like AWS or DigitalOcean) via the command line.

*   **Key Features:** Unified interface for containers and VMs, image-based workflow, and advanced clustering support.
*   **Installation:**
    ```bash
    sudo dnf install incus
    sudo systemctl enable --now incus.service
    # Run 'incus admin init' to set up networking and storage.
    ```

### Summary Comparison
| Manager | Ease of Use | Customization | Best Use Case |
| :--- | :--- | :--- | :--- |
| **GNOME Boxes** | Excellent | Low | Casual testing, Linux distros |
| **Virt-Manager** | Moderate | High | Daily driver VMs, Windows, GPU passthrough |
| **Quickemu** | High | Moderate | Fast setup of optimized Windows/macOS |
| **Cockpit** | Moderate | Moderate | Remote servers, headless systems |
| **Incus** | Moderate (CLI) | High | Dev-Ops, cloud-native workflows |

Do any of them support docker style networks? i.e. i can access any open port of the VM via an ip address
§a§
The short answer is **yes**, but how "Docker-like" the experience is depends on the manager you choose.

In the world of QEMU, "Docker-style" networking usually refers to **Bridge Networking** or **NAT with Host-to-Guest visibility**. This allows the VM to have its own internal IP address that your host can ping and connect to directly.

### 1. Incus (The Most "Docker-like" Experience)
Incus is the most similar to Docker because it was designed as a container manager that happens to support VMs.
*   **Networking:** By default, Incus creates a bridge (usually `incusbr0`). Every VM you launch automatically gets a private IP on this bridge.
*   **Access:** You can access any port on the VM immediately using that IP from your host.
*   **Commands:** It even feels like Docker:
    ```bash
    incus launch images:fedora/40 my-vm --vm
    incus list  # Shows you the IP address immediately
    ssh user@<vm-ip>
    ```

### 2. Virt-Manager / Cockpit (The "Libvirt" Way)
Both of these use `libvirt` as their backend. Libvirt creates a default network called `default` (on the `virbr0` interface).
*   **Networking:** By default, VMs get an IP in the `192.168.122.x` range.
*   **Access:** Your Fedora host can reach any port on the VM using this IP address without any extra configuration.
*   **Comparison:** This is exactly like the `docker0` bridge. The VM can see the internet, and the host can see the VM, but other devices on your physical WiFi/Ethernet cannot see the VM unless you set up a "Public Bridge."
*   **Pro Tip:** Use the command `virsh net-dhcp-leases default` to see the IP addresses of your running VMs.

### 3. Quickemu (The "Optimized" Way)
Quickemu is unique because it uses a mix of networking types depending on the OS, but it is moving toward easier bridge support.
*   **Networking:** It often uses "User Mode" (SLIRP) networking by default, which is **not** Docker-style (you can't ping the VM from the host easily).
*   **How to get Docker-style:** You have to specify `--bridge br0` or use a specialized configuration file to enable bridge mode. Once enabled, it behaves like a standard networked device.

### 4. GNOME Boxes (The Weakest for Networking)
GNOME Boxes is designed for simplicity, which unfortunately means it uses **SLIRP (User Networking)** by default.
*   **The Problem:** In default mode, the VM is "hidden" behind a very restrictive NAT. You cannot easily ping the VM or access its ports via an IP from your host.
*   **The Fix:** If you want Docker-style networking in GNOME Boxes, you have to manually edit the XML configuration to use the `libvirt` system bridge, which effectively turns it into a simpler version of Virt-Manager.

### Summary Recommendation

| If you want... | Use this Manager | Network Style |
| :--- | :--- | :--- |
| **A CLI that feels like Docker** | **Incus** | Private bridge (`incusbr0`) with direct IP access. |
| **A GUI with full control** | **Virt-Manager** | Standard `virbr0` bridge; works exactly like Docker's bridge. |
| **The VM to look like a real PC on your LAN** | **Cockpit / Virt-Manager** | Setup a "Bridge" to your physical NIC (e.g., `br0`). |

**One Fedora-specific tip:** Fedora uses `firewalld`. If you can't reach your VM even with the correct IP, you may need to ensure the `libvirt` zone is active:
```bash
sudo firewall-cmd --zone=libvirt --add-service=ssh --permanent
sudo firewall-cmd --reload
```

## Complete Solution: Fixing "Cannot get interface MTU on 'ThetaCode': No such device"

This error occurs because your VM is configured to use a **bridged network device named "ThetaCode"** that doesn't exist on your Fedora system. Here's everything you need to know to fix it:

---

## 🔍 Understanding the Problem

When you see this error, libvirt is trying to:
1. Start your VM
2. Attach it to a network bridge called `ThetaCode`
3. Query that bridge's MTU (Maximum Transmission Unit)
4. **Fail** because no such bridge exists on your system ,

This typically happens when:
- A VM was imported from another system with different network config
- You manually edited the VM's XML with an incorrect bridge name
- A previous network configuration was deleted but the VM still references it
- You're following a tutorial that assumed you had already created a specific bridge

---

## ✅ Solution 1: Switch to NAT (Recommended for Most Users)

This is the **easiest fix** and provides the "Docker-style" networking you asked about earlier (host can access VM ports via IP).

### Steps:
1. **Open virt-manager**
2. **Right-click your VM** → **Open** (or double-click)
3. Click the **Lightbulb icon** (Show virtual hardware details)
4. Select **NIC** from the left sidebar
5. Change **Network source** from "Bridged Device: ThetaCode" to:
   - **"NAT: default"** or
   - **"Virtual network 'default': NAT"**
6. Click **Apply**
7. Start the VM

### What You Get:
- VM gets IP in `192.168.122.x` range
- Host can ping and access any port on the VM
- VM has full internet access
- No additional configuration needed

### Verify the Default Network Exists:
```bash
# Check if default network is active
sudo virsh net-list --all

# If it shows "inactive" or is missing, start it:
sudo virsh net-start default
sudo virsh net-autostart default

# Check the bridge exists
ip addr show virbr0
```

If the default network is completely missing, recreate it:
```bash
cat > /tmp/default.xml << 'EOF'
<network>
  <name>default</name>
  <forward mode='nat'/>
  <bridge name='virbr0' stp='on' delay='0'/>
  <ip address='192.168.122.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.122.2' end='192.168.122.254'/>
    </dhcp>
  </ip>
</network>
EOF

sudo virsh net-define /tmp/default.xml
sudo virsh net-start default
sudo virsh net-autostart default
```

## 🔧 Solution 2: Create the Missing "ThetaCode" Bridge

If you specifically need a bridge named `ThetaCode` (e.g., for LAN visibility), create it:

### Option A: Using NetworkManager (Safest for Fedora Desktop)

```bash
# Find your active physical interface
ip link show
# Look for your main interface (e.g., enp0s3, eth0, wlp2s0)

# Create the bridge
sudo nmcli connection add type bridge ifname ThetaCode con-name ThetaCode

# Configure it for DHCP (or use static IP if needed)
sudo nmcli connection modify ThetaCode ipv4.method auto

# Add your physical interface as a bridge slave (replace enp0s3 with yours)
sudo nmcli connection add type ethernet con-name ThetaCode-slave ifname enp0s3 master ThetaCode

# Activate the bridge
sudo nmcli connection up ThetaCode

# Verify it exists
ip addr show ThetaCode
```

⚠️ **Warning**: This will temporarily disrupt your network connection as it reconfigures your physical interface.

### Option B: Using virsh (Fedora/RHEL Method)

```bash
# Replace enp0s3 with your actual interface name
sudo virsh iface-bridge enp0s3 ThetaCode
```

⚠️ **Warning**: This also disrupts network connectivity temporarily.

### Option C: Use Existing virbr0 Instead

Instead of creating a new bridge, just change your VM to use the existing `virbr0`:

1. In virt-manager: VM Settings → NIC
2. Network source: **"Bridged Device"**
3. Device name: **`virbr0`**
4. Click Apply

---

## 🛠️ Solution 3: Edit VM XML Directly

If virt-manager GUI isn't working, edit the XML directly:

```bash
# Shutdown the VM first (if running)
sudo virsh shutdown <vm-name>

# Edit the XML
sudo virsh edit <vm-name>
```

Find the `<interface>` section and change it from:
```xml
<interface type='bridge'>
  <source bridge='ThetaCode'/>
  <model type='virtio'/>
</interface>
```

To:
```xml
<interface type='network'>
  <source network='default'/>
  <model type='virtio'/>
</interface>
```

Save and exit (in vim/nano: `:wq` or `Ctrl+X`, then `Y`).

## 🔐 Important: Session vs System Mode

Fedora virt-manager can run in two modes, which affects networking:

| Mode | Connection URI | Networking Capabilities | Best For |
|------|---------------|------------------------|----------|
| **System** | `qemu:///system` | Full (bridges, NAT, custom networks) | Production, servers, advanced networking |
| **Session** | `qemu:///session` | Limited (user-mode NAT only) | Desktop testing, no root required |

### Check Which Mode You're Using:
In virt-manager, look at the connection name in the left sidebar:
- **"QEMU/KVM user session"** = Session mode (limited networking)
- **"QEMU/KVM system session"** = System mode (full networking)

### Switch to System Mode (if needed):
1. In virt-manager: **File** → **Add Connection**
2. Hypervisor: **QEMU/KVM**
3. Check **"Connect to local hypervisor"**
4. **Uncheck** "Enable user session" (or select "System session")
5. Click **Connect**
6. Delete the old "user session" connection if desired ,

## 🚨 Firewall Considerations

Fedora uses `firewalld`. If you can't reach your VM even with correct IP:

```bash
# Ensure libvirt zone is active
sudo firewall-cmd --zone=libvirt --add-service=ssh --permanent
sudo firewall-cmd --zone=libvirt --add-service=dns --permanent
sudo firewall-cmd --zone=libvirt --add-service=dhcp --permanent
sudo firewall-cmd --reload

# Verify
sudo firewall-cmd --zone=libvirt --list-all
```
