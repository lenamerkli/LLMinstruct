Docker is a platform for packaging, distributing, and running applications in lightweight, isolated containers. Key concepts and how they fit together:

- Image — a read-only, versioned template that contains an application and everything it needs to run (OS libraries, runtime, app code). Images are built from a Dockerfile.
- Container — a running instance of an image. Containers are isolated processes that share the host kernel but have their own filesystem, network namespace, and resource limits.
- Dockerfile — a text file with layered build instructions (FROM, RUN, COPY, CMD, etc.) used to build an image.
- Registry — a place to store and share images (Docker Hub, private registries). Pull to download images, push to upload.
- Layers — each Dockerfile instruction creates a layer; layers are cached and shared between images to save space and speed builds.
- Volumes — persistent storage for containers (keeps data outside container filesystem so it survives container removal).
- Networking — Docker provides virtual networks so containers can communicate (bridge, host, overlay for multi-host).
- Orchestration (not part of Docker Engine itself) — tools like Docker Compose (multi-container apps on one host) and Kubernetes (cluster-level scheduling) manage multi-container deployments.

Typical workflow (minimal steps):
1. Write a Dockerfile describing how to build the image.
2. Build the image: docker build -t myapp:1.0 .
3. Run a container: docker run -d --name myapp -p 8080:80 myapp:1.0
4. Push image to registry: docker push myrepo/myapp:1.0
5. Deploy/pull the image on other hosts or in orchestration platforms.

When to use Docker:
- Consistent development and production environments.
- Microservices and multi-container applications.
- Isolation of app dependencies without full VMs.
- Faster CI/CD and reproducible builds.

Trade-offs and limits:
- Containers share the host kernel — not full VMs; less isolation than VMs for some security models.
- Stateful workloads need careful volume and backup handling.
- Networking and storage complexity grows at scale (use orchestration).

Basic commands cheat-sheet:
- docker build -t name:tag .
- docker images (list images)
- docker run -d -p hostPort:containerPort --name name image:tag
- docker ps (running containers) / docker ps -a (all)
- docker logs <container>
- docker exec -it <container> /bin/sh (open shell)
- docker stop/start/restart <container>
- docker rm <container> / docker rmi <image>

How do volumes work?
§a§
## How Docker volumes work

### What a volume is
A volume is a managed, persistent directory stored outside a container’s writable layer that containers can mount to read/write data. Volumes persist after the container is removed and are the recommended way to store container data.

### Types of Docker storage
- **Named volumes** — managed by Docker, created with docker volume create or implicitly when you mount by name. Docker stores them (usually under /var/lib/docker/volumes) and manages lifecycle.
- **Anonymous volumes** — created when you mount a path without a name (Docker assigns an ID). Useful for short-lived persistence.
- **Bind mounts** — map a specific host filesystem path into the container (docker run -v /host/path:/container/path). Docker doesn’t manage the contents; use when you need access to host files.
- **tmpfs mounts** — in-memory mounts (docker run --tmpfs) useful for ephemeral, high-speed storage that never touches disk.

### How to use volumes (common commands)
- Create a named volume:
  ```
  docker volume create mydata
  ```
- Run a container with a named volume:
  ```
  docker run -d --name app -v mydata:/data myimage
  ```
- Run with a bind mount:
  ```
  docker run -d -v /home/user/appdata:/data myimage
  ```
- List volumes:
  ```
  docker volume ls
  ```
- Inspect volume:
  ```
  docker volume inspect mydata
  ```
- Remove unused volumes:
  ```
  docker volume prune
  ```
- Remove a specific volume (must be unused by containers):
  ```
  docker volume rm mydata
  ```

### Behavior and semantics
- Data written to a mounted volume is stored on the host (or external volume driver) and outlives the container.
- If you mount a volume into a container directory that already contains files in the image, Docker copies the files from the image into the new volume the first time it’s created (named or anonymous) — this is called "populate on create."
- Multiple containers can mount the same volume simultaneously (good for sharing data), but concurrency and consistency are the app’s responsibility unless using a driver that provides locking/clustering.
- Bind mounts reflect host file permissions and ownership; named volumes use Docker-managed ownership (may default to root inside container). Use user mapping or chown in Dockerfile/entrypoint if needed.

### Performance and drivers
- Default local volumes are usually fast and suitable for most workloads.
- For production/stateful use across multiple hosts, use volume drivers (NFS, Ceph, EBS, Azure Disk/File, etc.) or orchestrator storage classes (Kubernetes) to provide distributed, durable storage.
- tmpfs is fastest (RAM), but ephemeral.

### Best practices
- Use named volumes for persistent app data (databases, uploads).
- Use bind mounts for development (live-editing code) and when you need direct host file access.
- Don’t store important persistent data in the container writable layer — it’s removed when the container is removed.
- Manage backups and snapshots at the volume/host level or via a supported volume driver.
- Be explicit about permissions: ensure UID/GID inside the container can access volume paths.

How does a volume show up in the container?
§a§
When you mount a volume into a container it appears as a normal directory at the mount path inside the container’s filesystem. Concretely:

- Mounting syntax (docker run):
  ```
  docker run -v myvol:/app/data myimage
  ```
  Inside the container you’ll see /app/data as a regular directory you can read/write.

- Bind mount example:
  ```
  docker run -v /host/path:/app/data myimage
  ```
  /app/data shows the files from /host/path.

- Behavior details:
  - If the image has files at the mount path and you mount a new named volume there, Docker will copy those image files into the newly created volume on first use (populate-on-create). After that the volume’s contents are what the container sees.
  - Permissions/ownership are determined by the host filesystem or the volume driver; inside the container the directory will have those UID/GID and permission bits.
  - Multiple containers mounting the same volume see the same files at that mount path (concurrency/locking is your app’s responsibility).
  - If you mount a tmpfs, the directory exists in memory and is empty on container start.

- Inspect inside container:
  - Use docker exec -it <container> /bin/sh (or /bin/bash) and ls /path to view the mounted directory.
  - To check mount metadata from the host: docker inspect <container> and look at Mounts (shows Source, Destination, Mode, RW, Type).

Would a persistent home directory work?
§a§
Yes — you can persist a user's home directory by mounting a volume (named volume or bind mount) at the user's home path inside the container (e.g., /home/alice). That will make the home directory survive container restarts and recreation.

Key points and recommendations:
- Use a named volume for portability and Docker-managed storage:
  - docker run -v alice-home:/home/alice myimage
- Use a bind mount to persist to a specific host path (useful for backups or multi-service access):
  - docker run -v /srv/alice-home:/home/alice myimage
- Ensure correct ownership/UID:GID inside the container:
  - If the container user UID differs from files’ ownership on the host, either create the user with the same UID in the image, adjust ownership at container start (chown), or use bind-mounted files with matching permissions.
- Populate-on-create: if you mount a new named volume onto /home/alice and the image already contains files there, Docker copies those files into the volume the first time — useful to seed a home dir.
- Backups and portability: bind mounts make backups easier (host path), named volumes require docker volume inspect to find the host path or use docker volume export/driver tooling.
- Concurrency and security: multiple containers mounting the same home can cause conflicts; use single-writer patterns or proper locking. Be careful exposing host-sensitive paths via bind mounts.
- tmpfs is not persistent — don’t use it for a persistent home.

Example (named volume):
  docker volume create alice-home
  docker run -d --name alice -v alice-home:/home/alice myimage

Example (bind mount with UID alignment):
  docker run -d -v /srv/alice-home:/home/alice --user 1000:1000 myimage
